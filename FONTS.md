# Пайплайн битмап-шрифтов (`scripts/font/`)

Этот документ - подробный техничеcкий разбор того, как в проекте генерируются pixel-perfect bitmap-style TTF-шрифты (`public/win-55-ui/font/*.ttf`), почему пайплайн устроен именно так, и какие грабли уже были найдены и обойдены. Краткая версия команд - в `CLAUDE.md`; здесь - "почему", а не только "как".

## Зачем это вообще нужно

В этом параграфе будет первый и последний мат всего репозитория. Заранее извините. Отрендерить pixel-perfect bitmap-style шрифт в браузере - ВЕЛИКАЯ ЁБКА, ДРОЧЬ И СОДОМИЯ. Сначала я пробовал делать это руками через FontForge, и задача была ну просто отбитая. Прогнать в TTF->BDF->TTF с выдержкой всех размерностей, для каждого стиля. И чтоб ещё и рендерилось без всякого дерьма.

`npm run font -- <command>` заменяет всё это детерминированным CLI-инструментом. Жёсткое требование с самого начала: **ноль внешне устанавливаемых инструментов** - ни FontForge, ни AutoTrace, ни Python. Всё - обычные npm-зависимости (кроме одного системного компонента Windows, см. "Растеризация: DirectWrite" ниже - это осознанный, а не случайный компромисс).

## Пайплайн целиком

```
source.ttf --strike--> .bdf --[fallback + merge]--> .bdf --(ручная правка)--> build --> .ttf --push-fonts--> public/
                                                                            \-> tofu --> {name}-TofuMaker.ttf -^
```

1. **`strike`** - растеризация векторного TTF в bitmap-страйк для конкретного pixel size, через DirectWrite (`directwrite.ts`, см. "Растеризация: DirectWrite" ниже). Строго bilevel, без anti-aliasing. На этом же шаге, если явно запрошен авто-кернинг (см. ниже), собственные BBX/DWIDTH исходного шрифта отбрасываются в пользу собственного правила.
2. **`fallback`** - механически то же самое (`strike` по другому исходнику), отдельная команда только ради явного намерения и отдельного суффикса файла.
3. **`merge`** - донабирает в primary BDF глифы, которых там физически нет, из fallback BDF. Пустой (по факту, но присутствующий) глиф типа `space` не считается "дырой" и не перезаписывается - только явный allowlist по префиксу имени (`space`, `nbspace`). Требует совпадения `SIZE` у обоих файлов - это именно та проверка, которая ловит исторические ошибки вида "страйк 12px по имени, а на самом деле 120px".
4. **Ручная правка BDF.** BDF - не промежуточный мусор, а сам QA-артефакт: простой текстовый формат, редактируется 1:1 в любом текстовом редакторе. Никакого PNG-превью или контактных листов - это пиксель-арт, смотреть нужно как есть. Для самого битмапа (не BBX/DWIDTH/свойств - те всё равно только текстом) есть `npm run charedit -- <bdf> [glyph]` (`scripts/font/src/charedit.ts`) - TUI поверх того же `parseBdf`/`writeBdf`: стрелки двигают курсор, space переключает пиксель, `[`/`]` листают глифы, `g` - переход по имени/кодпоинту/символу, `s` - сохранить. Никакого undo и никакой правки метаданных - тот случай, когда быстрее выделить пиксель курсором, чем считать биты в hex-строке руками. `<bdf>` без абсолютного пути резолвится относительно `src-font/` (можно звать просто `npm run charedit -- LiberationSans-Bold-24.bdf`, без префикса).

   При выходе, если хоть одна правка была сохранена (`s`), `charedit` сам вызывает `facePipeline.ts` (`scripts/font/src/facePipeline.ts`) - находит в манифесте все грани, у которых отредактированный BDF стоит в `strikeBdf`, `mergePath` или любом из `fallbackBdf` (один и тот же fallback-файл может быть общим сразу для нескольких граней - см. "`fonts.json`" ниже), и для каждой безусловно перезапускает re-merge (если редактировался `strikeBdf`/`fallbackBdf`, а не сам `mergePath` - иначе merge просто затёр бы правку, сделанную прямо в уже смёрженном файле) → `build` → `tofu` → `push-fonts`, всегда перезаписывая. В отличие от `strike-all`/`build-all`/... из `cli.ts`, которые нарочно пропускают уже существующий файл - здесь наоборот, оверрайт обязателен, это и есть весь смысл. Если `npm run dev` запущен, Vite сам делает `full-reload` при изменении файлов внутри `public/` (штатное поведение, ничего специально настраивать не пришлось) - обновлённый шрифт виден в браузере сразу после выхода из `charedit`.
5. **`build`** - растровый BDF -> outline TTF. Дальше самое интересное, см. "Устройство `build`" ниже.
6. **`tofu`** - строит из `?`-глифа того же BDF однострочный шрифт-компаньон, покрывающий весь Unicode - см. "TofuMaker" ниже.
7. **`push-fonts`** - копирует готовые TTF (основной + TofuMaker) из `src-font/` в `public/win-55-ui/font/`. Всегда перезаписывает - это финальный шаг публикации, а не генерация промежуточного артефакта, который могли отредактировать руками.
8. **`update-register`** - полностью перегенерирует `SUPPORTED_FACES` (`src/helpers/generatedFonts.ts`) и `@font-face`-блоки (`src/generated-fonts.css`, по два на грань - основной шрифт и его TofuMaker) из манифеста `src-font/fonts.json`.
9. **`all`** - `strike` (+ `fallback` + `merge`, если передан `--fallback-source`), затем печатает подсказку по следующим шагам. Дальше - снова руками: посмотреть BDF, `build`, `tofu`, `push-fonts`.
10. **`check`** - быстрая структурная валидация BDF (битые/дублирующиеся глифы, число "пустых" глифов) без полного `build`.

Всё вышеперечисленное - однократный, одношрифтовый пайплайн. Тот же набор шагов, но сразу по всем шрифтам и управляемый декларативно через `fonts.json`, - `strike-all`/`fallback-all`/`merge-all`/`build-all`/`tofu-all`/`push-fonts`/`update-register`, см. "`fonts.json`" ниже. `full-pipeline-all` прогоняет все семь по порядку одной командой, с progress bar по стадиям.

## Растеризация: DirectWrite (`directwrite.ts`)

`strike`/`fallback` растеризуют исходный векторный шрифт через DirectWrite - штатный текстовый движок Windows (`dwrite.dll`), а не через кросс-платформенную библиотеку вроде FreeType. У одного и того же исходного шрифта, на одном и том же размере, DirectWrite в режиме `DWRITE_RENDERING_MODE_ALIASED` (строго bilevel, с хинтингом, без сглаживания) даёт заметно более чистый растр, чем FreeType - причём разница не зависит ни от выбора между native TrueType hints и autohinter-ом FreeType, ни от версии его байткод-интерпретатора (35/38/40, свойство `interpreter-version`): все комбинации дают идентичный, чуть более грубый результат. Например, при 12px строчная `S` из Liberation Sans через FreeType получает на пиксель больше в одном месте контура (несимметричный "хвостик"), которого через DirectWrite просто нет.

DirectWrite - это именно то, через что реальные Windows-приложения для pixel-art (например, Aseprite) рисуют текст: Aseprite использует рендер-бэкенд Skia, который на Windows сам делегирует растеризацию шрифтов DirectWrite. Чтобы получить побитово такой же результат, нужен сам DirectWrite, а не приближение к нему средствами FreeType.

### Почему через FFI, а не нативный аддон или Skia

DirectWrite - COM API. В отличие от произвольной C++-библиотеки (в том числе самого Skia), у COM-интерфейсов есть жёсткая, версионированная бинарная стабильность: раскладка vtable зафиксирована навсегда для конкретного GUID интерфейса, вызывающая сторона может быть на любом языке, скомпилированном отдельно, без общих заголовков. Это ровно то, что делает разумным вызывать DirectWrite напрямую из Node через `koffi` (FFI-библиотека для вызова произвольных функций по адресу, без компиляции нативного аддона и без build-тулчейна) - метод интерфейса вызывается как сырой указатель на функцию, прочитанный из vtable по фиксированному смещению.

GUID-ы интерфейсов и порядок методов в vtable (`directwrite.ts`) сверены с автосгенерированными из официальной Microsoft win32metadata Rust-биндингами (`windows-rs`), а не взяты из документации на веру: страницы `learn.microsoft.com` перечисляют методы интерфейса в алфавитном порядке, а не в порядке vtable, и полагаться на них для диспетчеризации нельзя - расхождение на один слот означает вызов не той функции с не той сигнатурой, то есть повреждение памяти или падение процесса, а не понятную ошибку компиляции.

Каждый COM-интерфейс наследуется от `IUnknown`, чьи три метода (`QueryInterface`/`AddRef`/`Release`) всегда занимают слоты vtable 0-2 перед собственными методами интерфейса, которые начинаются со слота 3. `vtableSlot()` в `directwrite.ts` принимает 0-based индекс метода **внутри списка методов самого интерфейса** (в том порядке, в котором они перечислены в `windows-rs`) и сама прибавляет это смещение.

Skia сюда намеренно не подключали: единственная форма Skia, устанавливаемая как npm-пакет (`canvaskit-wasm`), скомпилирована в WASM и поэтому физически не имеет доступа к нативным OS API вроде DirectWrite - она всегда падает обратно на FreeType, независимо от платформы, на которой выполняется. Skia как зависимость дал бы второй FreeType-based рендер, не более близкий к результату Aseprite, чем уже использовавшийся.

### Метрики

Ширина продвижения (advance width) берётся через `IDWriteFontFace::GetGdiCompatibleGlyphMetrics` с `useGdiNatural=false` ("GDI Classic" - более старый и грубый из двух режимов хинтинга DirectWrite; `useGdiNatural=true` ближе к современному ClearType-стилю и не подходит эстетике проекта), а не через "сырые" design-metrics (`GetDesignGlyphMetrics`): они не хинтованы и на части глифов дают на целый пиксель больше, чем реально видно на растре.

В отличие от FreeType, у DirectWrite нет отдельной оси "native hint-инструкции шрифта vs autohinter" - режим `ALIASED` всегда использует один и тот же алгоритм хинтинга, поэтому флага `--hinting`, который был у версии пайплайна на FreeType, здесь нет.

### Следствие: генерация шрифтов - Windows-only

`dwrite.dll` - системный компонент Windows (с Vista SP2), не отдельно устанавливаемая библиотека, так что требование "ноль внешне устанавливаемых инструментов" по-прежнему в силе. Но сама генерация теперь непереносима на другие ОС - это осознанный компромисс ради результата, неотличимого от нативного Windows-рендеринга, а не случайное ограничение. Это касается только `scripts/font/` (build-time инструмент); сама библиотека `win-55-ui-vue` остаётся обычным кросс-платформенным Vue-пакетом, и уже собранные `.ttf` в `public/win-55-ui/font/` рендерятся в браузере на любой ОС как обычные веб-шрифты.

## Авто-кернинг (`rasterize.ts`, `autoRightGap`)

Рендер-движок отдаёт свои собственные left/right bearing вместе с растром - это design-metrics исходного векторного шрифта, а не то, что нужно пиксель-арту. Поэтому `rasterizeFont` умеет поверх них считать свои - но только если это явно запрошено: **по умолчанию авто-кернинг выключен**, и `strike`/`fallback` используют BBX/DWIDTH напрямую от рендер-движка. Включается флагом `--generate-kerning` в CLI, либо (в манифест-driven пайплайне) самим фактом присутствия ключа `kerning` у записи в `fonts.json` - см. ниже. Он того не стоит на крупных страйках, где исходные bearing и так достаточно точные; выигрыш заметен в первую очередь на маленьких pixel size, где лишняя колонка bearing - это заметная доля от ширины глифа.

Когда включён, правило такое:

- **Левый зазор всегда 0** (`bbx.xoff = 0` безусловно, для каждого глифа) - никакого left side bearing, глиф всегда прижат к origin.
- **Правый зазор** зависит от того, алфавитный ли это символ (`\p{Alphabetic}`, юникодное свойство - покрывает разом латиницу, кириллицу, греческий, армянский, иврит и т.д., а не только ASCII):
  - нет чернил в глифе вообще (пробел и т.п.) -> зазор всегда `3`, независимо от алфавитности - это отдельный, самый приоритетный случай, а не "хвост/tail";
  - **не алфавитный символ** (пунктуация, математические операторы, цифры, что угодно ещё) -> зазор всегда `flatRightSideGap` (default `1`). Эвристика по столбцу ниже для них не считается вовсе: дефис, `+`, `=` и т.п. равномерно тонкие по всей своей ширине, а не только у одного края, как хвост буквы - эвристика ниже приняла бы их за "хвост" и оставила бы вообще без зазора.
  - **алфавитный символ** -> ищем самый правый столбец растра, в котором вообще есть чернила (это не обязательно последний столбец bitmap - у пустого глифа типа `space` bitmap 1x1, но нулевой), суммируем чернила по `rightSideCount` столбцам (default `1`), считая от него влево, и сравниваем с `rightSideVolume` (default `1`): `<=` -> "хвост" (тонкая диагональ вроде `y`, `,`, `/`) -> зазор `tailRightSideGap` (default `0`); иначе -> "плоский" правый край (`o`, `l`, `m`) -> зазор `flatRightSideGap` (default `1`).
- `DWIDTH = bbx.w + правый_зазор`.

Все четыре порога настраиваются флагами `strike`/`fallback`: `--right-side-count`, `--right-side-volume`, `--flat-right-side-gap`, `--tail-right-side-gap` (в манифесте - соответствующими полями объекта `kerning`, camelCase). Пороги по умолчанию подобраны на глаз по Liberation Sans - для сильно другого исходного шрифта их может понадобиться пересмотреть.

`SWIDTH` (scalable width) при этом всегда считается отдельно, независимо от режима кернинга - он не участвует в `build` (только для BDF-спека/round-trip), так что рассинхронизация с DWIDTH тут ожидаема и не проблема.

## Вертикальные метрики: FONT_ASCENT/FONT_DESCENT (`rasterize.ts`, `verticalMetrics.ts`)

### Откуда берётся значение

`FONT_ASCENT`/`FONT_DESCENT` (позже - `hhea`/`sTypo` ascender/descender в TTF, то, из чего браузер считает высоту line-box при `line-height: 1`) считаются не из метрик исходного векторного шрифта, а из **фактических чернил уже растеризованного, хинтованного битмапа**. Наивная формула (`hhea.ascender / unitsPerEm * pixelSize`, округлённая) для Liberation Sans на 12px даёт 11/1 - но реальные чернила базовой латиницы (заглавные, строчные, цифры) занимают только 9 строк сверху и 2 снизу: целый пиксель нижних выносных элементов (`g`, `y`, `p`, `q`, `j`, хвост `Q`) при 11/1 оказывается ниже заявленной границы line-box, зазор между строками при `line-height: 1` съедается, и нижние выносные соседних строк могут зрительно соприкасаться.

Функция `computeVerticalMetrics` в `rasterize.ts` вместо этого меряет реальный битмап: берёт базовую латиницу (`A-Za-z0-9`) из уже растеризованных на этом шаге глифов (либо, если её нет вообще - например, страйк только кириллицы - все растеризованные глифы как fallback), находит максимальный реальный ascent и descent среди них, отдаёт оставшийся зазор (`pixelSize` минус реальный descent) под ascent. Для Liberation Sans на 12px это даёт 10/2.

Специально не берётся весь репертуар глифов без ограничения: редкие акцентированные заглавные или математические символы могут по-настоящему выходить за пределы 12 строк (у Liberation Sans, например, кириллическая `Й` реально достигает всех 12 строк) - включать их в расчёт раздуло бы "нормальные" метрики ради редких выбросов.

### Почему один страйк не может решить это в одиночку: `verticalMetrics.ts`

Разные начертания одного размера (Regular/Bold/Italic/BoldItalic) должны декларировать **одинаковые** ascent/descent - не потому что так удобнее, а потому что иначе ломается пиксель-в-пиксель совместимость при смешивании начертаний. Сумма (ascent+descent = pixelSize) не меняется в любом случае - `line-height` как таковой не съезжает. Ломается другое: всё, что позиционирует контент относительно того, где именно внутри line-box сидят чернила, а не относительно box'а целиком - например, заголовок окна сидит во flex-строке фиксированной высоты с `align-items: center`, и смещение ascent на 1px (даже без изменения суммы) сдвигает видимый текст на 1px внутри этой центрированной строки. У жирного начертания реальный descent обычно на пиксель больше, чем у обычного (нижние выносные элементы физически толще и чуть глубже) - если считать ascent/descent независимо для каждого начертания, Bold и Regular одного размера расходятся, и что-то, завязанное на позицию текста внутри фиксированной высоты, визуально прыгает при смене начертания.

Решение - `verticalMetrics.ts`: первое начертание, застриканное для пары (`fontName`, `pixelSize`) - по порядку в `fonts.json` это всегда `Regular` - меряет свои реальные чернила и кэширует результат в `src-font/{fontName}-{pixelSize}.measurements.json` (например `Standard-12.measurements.json`). Любое следующее начертание того же `fontName`+`pixelSize` (Bold, Italic, BoldItalic) читает этот кэш и использует его значения **вместо** собственного измерения.

Если у более позднего начертания реальные чернила глубже/выше, чем в кэше, это не глушится молча - `resolveVerticalMetrics` возвращает список `overflow`, и `cli.ts` печатает `console.warn` с точными числами. Сам глиф при этом не обрезается (браузер рисует контур как есть, метрики влияют только на line-box), риск - чисто визуальный: нижний пиксель глифа с глубоким descent-ом может зайти в пространство следующей строки при плотной вёрстке.

Кэш-файл `*.measurements.json` - обычный отслеживаемый файл в `src-font/`, не игнорируется (в отличие от `*.report.json`). Чтобы пересчитать метрики с нуля для конкретного размера, достаточно удалить соответствующий `{fontName}-{pixelSize}.measurements.json` и перестрикать заново, начиная с `Regular` (порядок важен - см. "Известные ограничения" ниже).

Кэширование применяется только к **первичному** страйку (`strike`/`strike-all`), не к `fallback`/`fallback-all`: у fallback-BDF своих `FONT_ASCENT`/`FONT_DESCENT` всё равно не доживают до финального шрифта (`merge` сохраняет свойства primary без изменений), так что измерять/кэшировать их не нужно - и опасно, если fallback (например, с совершенно другими пропорциями иероглифов) вдруг застрикан раньше primary и успел бы засеять кэш неподходящими числами.

## `fonts.json`: манифест-driven пайплайн (`fontsManifest.ts`, `register.ts`)

Одиночный пайплайн (см. выше) работает с одним шрифтом за раз. `src-font/fonts.json` - декларативный источник истины поверх него, сразу для всех граней: и про то, из чего собирается каждая грань (`fontName`/`style`/`size`, исходный TTF, промежуточные BDF, кернинг), и про то, что в итоге видит браузер (`SUPPORTED_FACES`, `@font-face`). Схема одной записи (`FaceEntry` в `fontsManifest.ts`), все пути - относительно `src-font/`:

- `fontName`, `style`, `size`, `ttf` - обязательные. `ttf` - имя файла TTF в `src-font/`, оно же имя файла, под которым `push-fonts` копирует его в `public/win-55-ui/font/`. Имя TofuMaker-компаньона (`{ttf}` с `.ttf` на `-TofuMaker.ttf`) выводится из него автоматически (`tofuTtfFilename()`) - отдельного поля в манифесте для этого нет.
- `source` + `strikeBdf` - исходный векторный шрифт и куда `strike-all` кладёт результат растеризации. `strikeBdf` - тот самый человеко-редактируемый BDF из шага 4 одиночного пайплайна.
- `fallbackSource` + `fallbackBdf` - **массивы**, той же длины, в том же порядке. `merge-all` сворачивает их в один BDF последовательно, от первого к последнему (второй fallback добирает то, что не нашлось ни в primary, ни в первом fallback, и т.д.) - можно подключить сразу несколько fallback-источников (например разные шрифты для разных диапазонов Unicode), а не один.
- `mergePath` - куда `merge-all` пишет результат слияния. Существует отдельно от `strikeBdf`, потому что это разные файлы: `strikeBdf` - страйк только основного источника (то, что реально редактируют руками), `mergePath` - страйк с уже подмешанными fallback-глифами (то, из чего собирают TTF). Для грани без fallback-ов `mergePath` не нужен вовсе.
- BDF, который реально идёт в `build-all`/`tofu-all`, - это `mergePath ?? strikeBdf`: если fallback-ов нет, строим прямо из `strikeBdf`.
- `kerning` - см. "Авто-кернинг" выше. Присутствие ключа само по себе включает авто-кернинг для этой грани; поля внутри (`rightSideCount`, `rightSideVolume`, `flatRightSideGap`, `tailRightSideGap`) все опциональны и по отдельности переопределяют дефолты. Пустой объект `{}` означает "авто-кернинг включён, все пороги по умолчанию".

Команды `strike-all`/`fallback-all`/`merge-all`/`build-all`/`tofu-all` проходят по всем записям манифеста и выполняют для каждой соответствующий одиночный шаг, но только если целевой файл ещё не существует - если существует, запись пропускается с `console.warn`, а не валит весь батч (в отличие от одиночных `strike`/`fallback`, которые без `--force` жёстко падают на существующем файле). Это осознанно: пересборка "только недостающих кусочков" частично собранного набора (например, добавили новую грань в манифест, а остальные уже готовы) - рутинная операция, а не исключительная ситуация, которую нужно подтверждать флагом.

`push-fonts` и `update-register`, наоборот, **всегда** перезаписывают: `push-fonts` копирует `ttf` (+ TofuMaker-компаньон) из `src-font/` в `public/win-55-ui/font/` (это финальный шаг публикации - его смысл именно в том, чтобы обновить уже опубликованное), а `update-register` полностью перегенерирует `src/helpers/generatedFonts.ts` (`SUPPORTED_FACES`) и `src/generated-fonts.css` (по два `@font-face`-блока на грань) из манифеста - оба файла помечены баннером "AUTO-GENERATED, не редактировать руками", так что перезаписывать их целиком безопасно и корректно на каждый запуск. `typography.ts` импортирует `SUPPORTED_FACES` из первого, `index.css` подключает второй через `@import` - обе точки подключения прописываются один раз руками при заведении файла, `update-register` их не трогает, только содержимое самих generated-файлов.

`full-pipeline-all` прогоняет `strike-all` -> `fallback-all` -> `merge-all` -> `build-all` -> `tofu-all` -> `push-fonts` -> `update-register` одной командой, печатая прогресс-бар по стадиям перед каждой из них.

## Устройство `build`: от растра к вектору

### Трассировка контуров (`contours.ts`)

Замена AutoTrace - свой однопроходный directed-edge boundary tracer по 4-связности. Для каждого блока закрашенных пикселей одновременно строятся и внешние, и "дырочные" контуры (для `o`, `e`, `8` и т.п.) - без отдельного прохода поиска дыр и без явного сопоставления "какая дыра какому внешнему контуру принадлежит": правило трассировки само гарантирует противоположный знак winding для дыры относительно внешнего контура, а формату TrueType/OpenType для заливки нужен именно плоский список контуров + winding (nonzero fill rule), никакой явной иерархии. Коллинеарные точки схлопываются перед эмиссией - кривых нет вообще, только прямые линии (`lineTo`), потому что трассировать нечего кроме прямых углов растра.

Корректность проверяется инвариантом: сумма signed area всех контуров глифа обязана совпадать с числом закрашенных пикселей (`build.ts` проверяет это на каждом глифе и пишет soft finding при расхождении).

### Координаты и сетка (`unitsPerEm`)

`unitsPerEm = pixelSize * SCALE` (`SCALE = 100` по умолчанию, флаг `--units-per-em-scale`). Каждая координата контура - целое кратное `SCALE` по построению (`coordinate = pixelIndex * SCALE`), поэтому ручная перепроверка em-size, из-за которой раньше "плыл" второй и последующие символы в строке в ручном FontForge-процессе, здесь структурно невозможна - округлять нечего.

`SCALE = 100`, а не что-то около "пиксель = пара юнитов" (как было в старых hand-made шрифтах, где `unitsPerEm` совпадал с итоговым размером в CSS-пикселях, т.е. ~24 для 12px-страйка) - осознанный выбор: `svg2ttf` (см. ниже) применяет собственные проходы упрощения геометрии с фиксированными допусками (~0.3-1.1 юнита). При крупном `unitsPerEm` эти допуски на порядки меньше расстояния между соседними пиксельными границами (100 юнитов) и гарантированно не трогают реальную геометрию; при мелком `unitsPerEm` тот же допуск мог бы случайно схлопнуть тонкие штрихи.

### Отчёт: soft findings vs hard errors

Проверки идут всегда, но не блокируют результат молча. Жёсткая ошибка на уровне глифа (например, вырожденный контур из повреждённого битмапа) - не валит всю сборку: такой глиф просто пропускается (`report.skipped`), пишется причина, а TTF всё равно собирается из всех остальных глифов. Так всегда есть что открыть и с чем свериться по отчёту, а не пустота при первой же проблеме в одном хэндэдитнутом глифе. Всё остальное - soft finding в `report.flagged` (несовпадение размеров битмапа и BBX, нулевой advance width у глифа с чернилами, дубли encoding и т.д.): TTF собирается, находки просто перечисляются в `<out>.report.json` и кратко в консоли. Отдельно есть `selfCheckRoundTrip` - билд перепарсивается и сверяется сам с собой (bbox/advance на пиксельной сетке), чтобы ловить собственные баги сериализации, а не только проблемы входных данных.

Модель специально спроектирована под то, как реально идёт работа: автоматика указывает, куда смотреть, а не заменяет собой визуальную проверку глазами.

## Почему `opentype.js` заменили на `svg2ttf`

`build.ts` собирает финальный TTF через `svg2ttf`, а не через `opentype.js`, хотя `opentype.js` в пайплайне присутствует и используется в других местах (парсинг исходных векторных шрифтов в `rasterize.ts`, `selfCheckRoundTrip` в `build.ts` - оба раза только на чтение). Причина: `opentype.js` в принципе не умеет писать классический TrueType (`glyf`/`loca`) - только CFF-flavored OpenType. Это видно прямо в `dist`-бандле библиотеки: `Font.prototype.toTables()` вызывает единственную нефорковую функцию `sfnt.fontToTable()`, которая безусловно строит `cffTable`; таблицы `glyf`/`loca` в этой библиотеке есть только в парсере (для чтения существующих шрифтов), не в райтере.

Это принципиально, а не косметически: механизм, за счёт которого Windows рисует уже выровненные по пиксельной сетке контуры вообще без размытия (см. `gasp` ниже), специфичен именно для TrueType. Для CFF-контуров на Windows такого пути нет - там почти всегда работает обычное grayscale-сглаживание, независимо от того, насколько точно выровнена геометрия.

`svg2ttf` (та же `nodeca`/fontello-экосистема, что и растеризация раньше использовала через `lv_font_conv`) пишет настоящие `glyf`/`loca`-таблицы из SVG-путей. Контуры этого пайплайна - только прямые линии, поэтому сериализация тривиальна (`svgFont.ts`: `contourToSvgPath()` строит `M x,y L x,y ... Z`).

Бонус: `svg2ttf` уже по умолчанию выставляет `head.flags = 0x000B` (биты "baseline at y=0", "LSB at x=0", "force integer ppem for scaler math") и `OS/2.fsSelection = REGULAR | USE_TYPO_METRICS` - без единой лишней строчки кода с нашей стороны (см. "Другие найденные и исправленные баги" про то, зачем нужен именно этот бит).

## `gasp`: почему шрифт вообще выглядит чётко на Windows

`svg2ttf` не пишет таблицу `gasp` вовсе. Windows использует её, чтобы решить, применять ли grayscale-сглаживание к контуру шрифта на конкретном диапазоне размеров (ppem): один диапазон на весь ppem (`0..65535`) с флагом `DOGRAY` (без `GRIDFIT`) даёт ровно то, что нужно - AA формально включено, но контур уже выровнен по пиксельной сетке, так что каждой границе просто нечего усреднять, и результат получается чётким без сглаживающего "дребезга".

`build.ts` дописывает такую таблицу постфактум через `sfnt.ts` (`insertSfntTable`) - маленький, независимый от gasp как такового бинарный инструмент: перечитывает directory таблиц sfnt-контейнера, добавляет новую запись, пересчитывает офсеты/паддинг/чексуммы (включая `checkSumAdjustment` в `head`, который обязан учитывать вставленную таблицу).

## `cmap`: почему большие (fallback-merged) шрифты не грузились в браузере

`Standard-Regular-12` после fallback-мёрджа с крупным CJK-источником разрастается до десятков тысяч глифов. На такой плотности браузер (и Chrome, и Firefox) отказывается грузить шрифт с ошибкой OTS (`OpenType Sanitizer`, санитайзер, который оба прогоняют по любому скачанному `@font-face`-шрифту): `cmap: Failed to parse format 4 cmap subtable`.

Причина - в `svg2ttf`: его writer для cmap format 4 всегда использует полный `glyphIndexArray` + 16-битный `idRangeOffset` (никогда не применяет более компактный `idDelta`-шорткат). При достаточном числе сегментов/глифов в BMP-диапазоне (что рутинно случается после fallback-мёрджа) это поле переполняется. OTS ловит битую format-4-подтаблицу и, по спецификации, ронит **всю** таблицу `cmap` целиком - а с ней и весь шрифт.

Чинить кодирование format 4 внутри `svg2ttf` смысла нет: он и так безусловно пишет ещё и format 12 (полный диапазон Unicode, 32-битные поля - переполниться нечем), а format 12 - строгое надмножество format 4. Более того, парсер `opentype.js` сам предпочитает подтаблицу `(3,10)`/format 12 таблице `(3,1)`/format 4, если обе присутствуют. Значит, format 4 не нужен вовсе. Решение - `cmap.ts` (`stripCmapFormat4`): вырезать из уже собранной таблицы `cmap` подтаблицы format 4 и связанные с ними заголовки, пересобрать directory (с сохранением шаринга одного и того же блока данных между несколькими заголовками, если он есть), заменить таблицу через `sfnt.ts` (`replaceSfntTable`).

## TofuMaker: полный контроль над тем, какие глифы вообще существуют (`tofu.ts`)

У каждой собранной грани шрифта есть шрифт-компаньон - `{fontName}-{style}-{size}-TofuMaker.ttf`. Он состоит ровно из одного реального глифа (символ `?` из BDF этой же самой грани - в её собственном пиксельном стиле, не абстрактный плейсхолдер), сопоставленного буквально каждому валидному Unicode-кодпоинту.

Прописывается в CSS font-family последним перед `Arial, sans` (`typography.ts`, `typographyStyles()`): `{fontName}-{style}-{size}, {fontName}-{style}-{size}-TofuMaker, Arial, sans`. Смысл - убрать саму возможность того, что браузер соскочит с битмап-шрифта на системный для символа, которого нет ни в основном, ни в fallback-merged репертуаре: вместо гладкого системного глифа рисуется свой же пиксельный `?`. `Arial, sans` в самом конце остаётся на случай, если сам TofuMaker-шрифт по какой-то причине не загрузится - в норме до него дело не доходит.

### Почему без дублирования глифа: cmap format 13

Обычный способ сопоставить много кодпоинтов одному глифу - формат `cmap` 12 (группы `startCharCode`/`endCharCode`/`startGlyphID`), но там ID глифа внутри группы растёт линейно вместе с кодпоинтом (`glyphId = startGlyphID + (charCode - startCharCode)`) - для "все кодпоинты на один и тот же глиф" пришлось бы либо по записи на кодпоинт, либо реально дублировать глиф в `glyf`-таблице много раз.

Формат 13 - тот же самый бинарный layout групп, что и у формата 12, но с другой семантикой: `glyphId = startGlyphID` целиком для всего диапазона, без прибавления смещения. В спецификации OpenType он прямо описан как предназначенный для "last resort" шрифтов, покрывающих весь Unicode небольшим набором заглушек. Всё пространство Unicode (за вычетом диапазона суррогатных пар `D800-DFFF`, который в принципе не бывает настоящим кодпоинтом - используется только для кодирования UTF-16) сворачивается в 3 группы (`cmap.ts`, `FULL_UNICODE_RANGES`): до суррогатов, после них, и все astral-плоскости (`0x10000-0x10FFFF`). Реальный глиф в `glyf`-таблице всего один (плюс `.notdef` с той же формой на случай обращения к глифу 0 в обход cmap) - таблица `cmap` целиком занимает меньше сотни байт, независимо от того, сколько кодпоинтов она покрывает.

## Известные явления, которые не чинятся на уровне пайплайна

- **Firefox: горизонтальный суб-пиксельный дрейф.** Ни этот пайплайн, ни его предшественник не встраивают в шрифт TrueType hint-инструкции (`fpgm`/`prep`/побайтовые hint-программы на глиф) - "хинтинг" исчерпывается точными координатами контура, застывшими на этапе растеризации. Firefox прогоняет загруженные (`@font-face`) шрифты через свой собственный текстовый стек отдельно от системных шрифтов, и без реальных hint-инструкций там нет привязки к пиксельной сетке - только сглаживание по плавающим координатам. Отсюда - лёгкое накопление суб-пиксельной погрешности на протяжении строки. В Chrome (DirectWrite на Windows) тот же безынструкционный шрифт рендерится идеально ровно. Настоящий фикс потребовал бы генерации реальных TrueType hint-инструкций (например, через `ttfautohint`) - то есть возврата внешней зависимости, от которой пайплайн специально уходил.
- **ClearType/LCD-сглаживание: лёгкий цветной ореол по краю штрихов.** Инвариантная особенность LCD-subpixel-сглаживания как такового - его фильтр-ядро по конструкции "размазывает" покрытие на соседний субпиксель даже у идеально выровненной по сетке границы. Не зависит от точности геометрии шрифта. `-webkit-font-smoothing: none` переключает Chromium на grayscale-AA вместо ClearType, но не отключает антиалиасинг полностью - стандартного кросс-браузерного способа заставить браузер рисовать текст строго bilevel не существует. Настоящее решение потребовало бы рендерить текст через `<canvas>` побитмапно вместо настоящего `@font-face`-текста - совсем другая архитектура, вне рамок этого пайплайна.

Оба явления - характеристики рендер-стека браузера, применяются к любому `@font-face`-шрифту без embedded hints, а не к конкретно этому пайплайну или к качеству растеризации - раздел "Растеризация: DirectWrite" выше про другое: там речь о том, каким получается сам исходный растр, здесь - о том, как браузер потом рисует уже готовый контур на экране.

## Другие найденные и исправленные баги

- **`FONT_ASCENT`/`FONT_DESCENT` не суммировались в `PIXEL_SIZE`.** Независимое округление ascent и descent по отдельности не даёт гарантии, что сумма совпадёт с номинальным размером страйка. `build.ts` использует эту сумму как `hhea.ascender/descender` - а это именно то, из чего браузер считает высоту line-box при `line-height: 1`. Недостача в 1 юнит даёт systematic сдвиг текста на 1px вниз (лишний leading делится пополам сверху/снизу). Текущее поведение (`computeVerticalMetrics`, см. выше) гарантирует точную сумму по построению - descent измеряется, ascent выводится как остаток (`pixelSize - descent`), а не считается независимо.
- **`USE_TYPO_METRICS` не был выставлен.** Даже с точной суммой ascent+descent сдвиг не уходил - браузеры по умолчанию (без этого бита в `OS/2.fsSelection`) считают line-box не по `sTypoAscender/sTypoDescender` (которые как раз равны точным ascent/descent), а по `usWinAscent/usWinDescent`, которые многие писатели шрифтов (в том числе `opentype.js`) вычисляют автоматически из фактических экстремумов чернил по всем глифам собранного шрифта - величина, никак не связанная с декларированными ascent/descent. `svg2ttf` выставляет этот бит по умолчанию сам (см. выше).

## `paths.config.json`: раскладка репозитория одним файлом

Корень репозитория, не `src-font/` - расположение директорий, которые нужны build-инструментам (`src-font/`, `public/win-55-ui/font/`, `public/win-55-ui/emoji/`, `public/win-55-ui/x-emoji/`, `scripts/font/test/__fixtures__`, `src-font-tests/` - см. ниже, сгенерированные `generatedFonts.ts`/`generated-fonts.css`), плюс `publicUrlPrefix` (`/win-55-ui` - под каким URL Vite отдаёт `public/win-55-ui` в dev/build, используется в `register.ts` при генерации `@font-face { src: url(...) }`). Раньше это было продублировано в двух местах: `scripts/font/src/paths.ts` и `scripts/emoji-cli.js` каждый считали одни и те же пути независимо, вручную - переименование директории означало grep по обоим. Теперь оба читают этот файл (каждый сам, `readFileSync` + `JSON.parse` - поделиться кодом впрямую нельзя, `paths.ts` компилируется через tsc в `scripts/font/dist/src/`, `emoji-cli.js` - обычный JS, выполняется как есть). Только *имена файлов* внутри уже сконфигурированной директории (`fonts.json`, `emoji-registry.csv`, и т.д.) остаются литералами в коде - это конвенция конкретного парсера, а не факт о раскладке репозитория, конфигурировать их отдельно смысла нет.

Не путать с `plugin.js` (Vite-плагин `win55ui()` для npm-пакета, см. «npm-пакет» в `CLAUDE.md`) - он хардкодит `public/win-55-ui` намеренно: `paths.config.json` не публикуется вместе с пакетом (не входит в `files` в `package.json`), а `plugin.js` должен продолжать работать уже установленным из `node_modules` в чужом проекте, без доступа к этому репозиторию.

## Структура `scripts/font/`

TypeScript со своим `tsconfig.json` и build-шагом (`npm run font:build`, инкрементальный) - единственный инструмент в `scripts/` на TS, а не на обычном JS, как остальные `*-cli.js`: домен достаточно сложный (геометрия контуров, бинарные форматы BDF/sfnt, COM vtable dispatch), чтобы типы окупались.

`src/` и `test/` - раздельные директории (не `foo.ts` + `foo.test.ts` вперемешку в одной папке): `scripts/font/tsconfig.json`'s `rootDir` - `scripts/font` целиком (не `src`), `include` захватывает оба - `src/**/*.ts` и `test/**/*.ts`. Из-за этого `dist/` целиком отражает раскладку `rootDir`: `src/cli.ts` -> `dist/src/cli.js`, `test/bdf.test.ts` -> `dist/test/bdf.test.js` - на один уровень вложенности глубже, чем было бы при плоском `dist/*.js`. `npm run font`/`npm run charedit` запускают `dist/src/cli.js`/`dist/src/charedit.js` напрямую, `npm run font:test` - `node --test "dist/test/**/*.test.js"`; `paths.ts`'s `projectRoot` считает на один `..`-переход больше, чем считал бы для плоского `dist/`, см. комментарий в самом файле. Тестовые файлы импортируют из `src/` относительным путём `../src/имя-файла.js`, а не `./имя-файла.js`, как было бы при совместном расположении.

| Файл | Назначение |
|---|---|
| `cli.ts` | Разбор argv, диспетчеризация подкоманд, `usage()`/`fail()` |
| `charedit.ts` | `npm run charedit` - отдельный raw-mode TUI-инструмент (не подкоманда `cli.ts`, свой argv/жизненный цикл), редактирует битмап одного глифа BDF; на выходе вызывает `facePipeline.ts` |
| `cli-args.ts` | Ручной сканер `--flag value` (без внешних зависимостей типа yargs) |
| `paths.ts` | `projectRoot`/`srcFontDir`/`publicFontDir`/`publicUrlPrefix`/`fixturesDir`/`fontsManifestPath`/`generatedFontsTsPath`/`generatedFontsCssPath` - всё, кроме `projectRoot` (считается от `__dirname` - конфиг ещё нужно суметь найти) и `fontsManifestPath` (`fonts.json` - имя файла, конвенция самого `fontsManifest.ts`, не факт о раскладке репозитория), читается из `paths.config.json` в корне репозитория, см. ниже |
| `registry.ts` | `SIZES` - зеркало того же списка в `typography.ts`, для предупреждения при нестандартном размере страйка |
| `types.ts` | `BdfFont`, `BdfGlyph`, `Bbx`, `Point`, `Contour` и т.д. |
| `bdf.ts` | `parseBdf()`/`writeBdf()` - парсер и сериализатор BDF |
| `fontsManifest.ts` | `FaceEntry`/`FontsManifest`, `parseFontsManifest()`/`loadFontsManifest()` - схема и валидация `fonts.json`; `tofuTtfFilename()`/`tofuFamilyName()` - вывод имени TofuMaker-компаньона |
| `directwrite.ts` | Растеризация через DirectWrite: ручной COM vtable dispatch через `koffi` (см. "Растеризация: DirectWrite" выше). Windows-only |
| `rasterize.ts` | Векторный TTF/OTF -> `BdfFont`: вызывает `directwrite.ts` на каждый codepoint, плюс авто-кернинг (`autoRightGap`) и измерение вертикальных метрик по реальным чернилам (`computeVerticalMetrics`, см. выше) |
| `verticalMetrics.ts` | `resolveVerticalMetrics()` - кэш `FONT_ASCENT`/`FONT_DESCENT` на диске (`{fontName}-{pixelSize}.measurements.json`), общий для всех начертаний одного размера (см. выше) |
| `contours.ts` | Битмап глифа -> контуры (собственный boundary tracer, см. выше) |
| `svgFont.ts` | Контуры -> SVG path -> SVG-font XML-документ -> вызов `svg2ttf` |
| `sfnt.ts` | Низкоуровневые операции над sfnt-контейнером: `insertSfntTable`/`getSfntTable`/`replaceSfntTable`, генерация `gasp` |
| `cmap.ts` | `stripCmapFormat4` - вырезание переполняющейся format-4 cmap-подтаблицы; `buildTofuCmapTable` - построение format-13 "everything to one glyph" cmap для TofuMaker |
| `build.ts` | Оркестрация: BDF -> глифы -> `svgFont.ts` -> патчи `gasp`/`cmap` через `sfnt.ts` -> отчёт `flagged`/`skipped`. Также экспортирует переиспользуемый `buildGlyphUnsafe()` (один глиф BDF -> `SvgGlyphSpec`) для `tofu.ts` |
| `tofu.ts` | Оркестрация TofuMaker: берёт `?`-глиф из BDF, строит 2-глифовый (`.notdef` + `?`) шрифт, патчит `gasp` и format-13 `cmap` |
| `merge.ts` | Донабор недостающих глифов из fallback BDF, `summarizeBackfill()` (компактный range-summary, capped на 8 диапазонов) |
| `register.ts` | `buildSupportedFacesModule()`/`buildFontFaceCss()` - генерация полного содержимого `generatedFonts.ts`/`generated-fonts.css` из `FontsManifest`, включая TofuMaker-блоки (см. выше) |
| `facePipeline.ts` | `rebuildFace()`/`facesReferencingBdf()`/`rebuildFacesForBdf()` - "hand-edited a BDF, make the final font catch up": re-merge (если нужен) + build + tofu + push-fonts для одной грани, всегда с перезаписью (в отличие от `cmdMergeAll`/`cmdBuildAll`/`cmdTofuAll` в `cli.ts`, которые нарочно пропускают уже существующий файл). Используется и `charedit.ts` (на выходе), и `cli.ts` (`mergeChain`/`faceLabel` вынесены сюда, чтобы не дублировать) |
| `svg2ttf.d.ts` | Рукописная декларация типов - у пакета `svg2ttf` официальных `@types` нет |

Каждый `*.ts` в `src/` (кроме `svg2ttf.d.ts`) имеет пару `*.test.ts` в `test/`, тем же именем, на `node:test` (первый прецедент тестов в репозитории вообще, `npm run font:test`) - кроме `cli.ts` и `charedit.ts`, оба чистые argv/stdin-обвязки без собственной логики, вся тестируемая логика, которой они пользуются, живёт (и тестируется) в других файлах этой таблицы. Тесты по возможности не зависят от живых файлов в `src-font/` (которые пользователь может в любой момент перегенерировать/удалить) - либо замороженная фикстура (`fixturesDir`, физически `scripts/font/test/__fixtures__/`), либо растеризация на лету из стабильного исходника (`src-font/liberation_sans/` - читается, не пишется).

Тесты, которым реально нужно писать файлы, чтобы проверить path-зависимую логику (`mergeChain` в `facePipeline.test.ts`, `resolveVerticalMetrics`/`readCachedVerticalMetrics` в `verticalMetrics.test.ts`), пишут в `srcFontTestsDir` (`paths.ts`, физически `src-font-tests/` в корне репозитория, gitignored) - никогда не в реальный `src-font/` и не в `os.tmpdir()`. Раньше `verticalMetrics.test.ts` писал прямо в реальный `src-font/` (с рандомизированным `fontName`, чтобы не столкнуться с реальными данными, и `unlinkSync` в `finally`) - рабочее, но хрупкое решение: упавший на середине тест-ран оставлял мусорный `.measurements.json` прямо в рабочем дереве. `writeCachedVerticalMetrics()`/`readCachedVerticalMetrics()`/`resolveVerticalMetrics()` поэтому принимают необязательный `baseDir` (по умолчанию - настоящий `srcFontDir`, как и раньше в проде), которым тесты подменяют его на `srcFontTestsDir`. Тесты по-прежнему подчищают за собой (`finally` + `unlinkSync`/`rmSync`) - `src-font-tests/` не подчищается автоматически между прогонами, только внутри каждого теста. `facesReferencingBdf` тестируется чистыми путями относительно `srcFontDir`, без единого файла на диске; `rebuildFace`'s собственная запись в `srcFontDir`/`publicFontDir` тестами не покрыта - оба пути жёстко зашиты в `paths.ts` без параметра `baseDir` (в отличие от `verticalMetrics.ts`), без такого сэндбокса писать пришлось бы прямо в рабочее дерево пользователя.

## Известные ограничения / что не доделано

- Allowlist "пустой глиф - это нормально, не считать дырой" в `merge.ts` сейчас - только `space`/`nbspace`; скорее всего придётся расширять по мере использования новых fallback-источников.
- Правило авто-кернинга (см. выше) - эвристика (дефолтные пороги `rightSideCount`/`rightSideVolume` = 1), подобранная на глаз по Liberation Sans; для сильно другого исходного шрифта пороги может понадобиться пересмотреть через `kerning` в `fonts.json`.
- `merge-all` не умеет частичного слияния: если для грани не хватает хотя бы одного файла из цепочки (`strikeBdf` или любой `fallbackBdf`), пропускается вся грань целиком, а не сколько получится.
- `strike-all`/`fallback-all`/`build-all`/`tofu-all` не перезаписывают существующий файл никогда (нет batch-эквивалента `--force`) - для принудительной пересборки одной конкретной грани сейчас нужно удалить файл руками или вызвать одиночную команду (`strike`/`build`/`tofu`) с `--force`/явным `--out` напрямую.
- `cmdAll` (команда `all`) печатает подсказку по следующим шагам, оставшуюся от одиночного пайплайна до появления `fonts.json` - не упоминает `tofu` и ссылается на команду `register`, которой больше нет (заменена на `update-register`). Не влияет на корректность самой команды, только на текст подсказки.
- Real TrueType hinting instructions (`fpgm`/`prep`/per-glyph bytecode) в пайплайне принципиально нет - см. "Известные явления" выше. Если это когда-нибудь станет проблемой достаточно серьёзной, чтобы оправдать `ttfautohint` как зависимость (нарушив "zero externally-installed tools"), это отдельное архитектурное решение, не мелкий фикс.
- Генерация шрифтов работает только на Windows (см. "Растеризация: DirectWrite" выше) - осознанный, а не временный компромисс.
