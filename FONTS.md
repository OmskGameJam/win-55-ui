# Пайплайн битмап-шрифтов (`scripts/font/`)

Этот документ - подробный техничеcкий разбор того, как в проекте генерируются pixel-perfect bitmap-style TTF-шрифты (`public/win-55-ui/font/*.ttf`), почему пайплайн устроен именно так, и какие грабли уже были найдены и обойдены. Краткая версия команд - в `CLAUDE.md`; здесь - "почему", а не только "как".

## Зачем это вообще нужно

В этом параграфе будет первый и последний мат всего репозитория. Заранее извините. Отрендерить pixel-perfect bitmap-style шрифт в браузере - ВЕЛИКАЯ ЁБКА, ДРОЧЬ И СОДОМИЯ. Сначала я пробовал делать это руками через FontForge, и задача была ну просто отбитая. Прогнать в TTF->BDF->TTF с выдержкой всех размерностей, для каждого стиля. И чтоб ещё и рендерилось без всякого дерьма.

`npm run font -- <command>` заменяет всё это детерминированным CLI-инструментом. Жёсткое требование с самого начала: **ноль внешне устанавливаемых инструментов** - ни FontForge, ни AutoTrace, ни Python. Всё - обычные npm-зависимости.

## Пайплайн целиком

```
source.ttf --strike--> .bdf --[fallback + merge]--> .bdf --(ручная правка)--> build --> .ttf --push-fonts--> public/
```

1. **`strike`** - растеризация векторного TTF в bitmap-страйк для конкретного pixel size. Никакого anti-aliasing: `lv_font_conv`'s bundled FreeType WASM запускается в monochrome/hinted режиме (`FT_LOAD_TARGET_MONO`) - решение о цвете каждого пикселя принимает сам hint-интерпретатор шрифта, а не постфактум-threshold по grayscale-покрытию. Это то, что воспроизводит чистые 1px-линии на малых размерах (как в старом FontForge-процессе), а не "размытый" результат наивной супервыборки. На этом же шаге, если явно запрошен авто-кернинг (см. ниже), FreeType-шные BBX/DWIDTH от исходного векторного шрифта отбрасываются в пользу собственного правила.
2. **`fallback`** - механически то же самое (`strike` по другому исходнику), отдельная команда только ради явного намерения и отдельного суффикса файла.
3. **`merge`** - донабирает в primary BDF глифы, которых там физически нет, из fallback BDF. Пустой (по факту, но присутствующий) глиф типа `space` не считается "дырой" и не перезаписывается - только явный allowlist по префиксу имени (`space`, `nbspace`). Требует совпадения `SIZE` у обоих файлов - это именно та проверка, которая ловит исторические ошибки вида "страйк 12px по имени, а на самом деле 120px".
4. **Ручная правка BDF.** BDF - не промежуточный мусор, а сам QA-артефакт: простой текстовый формат, редактируется 1:1 в любом текстовом редакторе. Никакого PNG-превью или контактных листов - это пиксель-арт, смотреть нужно как есть.
5. **`build`** - растровый BDF -> outline TTF. Дальше самое интересное, см. ниже.
6. **`push-fonts`** - копирует готовый TTF из `src-font/` в `public/win-55-ui/font/`. Всегда перезаписывает - это финальный шаг публикации, а не генерация промежуточного артефакта, который могли отредактировать руками.
7. **`update-register`** - полностью перегенерирует `SUPPORTED_FACES` (`src/helpers/generatedFonts.ts`) и `@font-face`-блоки (`src/generated-fonts.css`) из манифеста `src-font/fonts.json`. Заменил собой старую команду `register`, которая печатала (или, с `--write`, вписывала текстовым сплайсом по anchor-комментариям) те же артефакты по одному шрифту за раз - см. «`fonts.json`: манифест-driven пайплайн» ниже про то, почему это изменилось.
8. **`all`** - `strike` (+ `fallback` + `merge`, если передан `--fallback-source`), затем печатает подсказку по следующим шагам. Дальше - снова руками: посмотреть BDF, `build`, `push-fonts`.
9. **`check`** - быстрая структурная валидация BDF (битые/дублирующиеся глифы, число "пустых" глифов) без полного `build`.

Всё вышеперечисленное - однократный, одношрифтовый пайплайн. Тот же набор шагов, но сразу по всем шрифтам и управляемый декларативно через `fonts.json`, - `strike-all`/`fallback-all`/`merge-all`/`build-all`/`push-fonts`/`update-register`, см. ниже.

## Авто-кернинг (`rasterize.ts`, `autoRightGap`)

FreeType отдаёт свои собственные left/right bearing вместе с растром - это design-metrics исходного векторного шрифта, а не то, что нужно пиксель-арту. Поэтому `rasterizeFont` умеет поверх них считать свои - но только если это явно запрошено: **по умолчанию авто-кернинг выключен**, и `strike`/`fallback` воспроизводят поведение до его появления бит-в-бит (BBX/DWIDTH напрямую от FreeType). Включается флагом `--generate-kerning` в CLI, либо (в манифест-driven пайплайне) самим фактом присутствия ключа `kerning` у записи в `fonts.json` - см. ниже. Он того не стоит на крупных страйках, где FreeType-шные bearing и так достаточно точные; выигрыш заметен в первую очередь на маленьких pixel size, где лишняя колонка bearing - это заметная доля от ширины глифа.

Когда включён, правило такое:

- **Левый зазор всегда 0** (`bbx.xoff = 0` безусловно, для каждого глифа) - никакого left side bearing, глиф всегда прижат к origin.
- **Правый зазор** зависит от того, алфавитный ли это символ (`\p{Alphabetic}`, юникодное свойство - покрывает разом латиницу, кириллицу, греческий, армянский, иврит и т.д., а не только ASCII):
  - нет чернил в глифе вообще (пробел и т.п.) -> зазор всегда `3`, независимо от алфавитности - это отдельный, самый приоритетный случай, а не "хвост/tail";
  - **не алфавитный символ** (пунктуация, математические операторы, цифры, что угодно ещё) -> зазор всегда `flatRightSideGap` (default `1`). Эвристика по столбцу ниже для них не считается вовсе: дефис, `+`, `=` и т.п. равномерно тонкие по всей своей ширине, а не только у одного края, как хвост буквы - эвристика ниже приняла бы их за "хвост" и оставила бы вообще без зазора.
  - **алфавитный символ** -> ищем самый правый столбец растра, в котором вообще есть чернила (это не обязательно последний столбец bitmap - у пустого глифа типа `space` bitmap 1x1, но нулевой), суммируем чернила по `rightSideCount` столбцам (default `1`), считая от него влево, и сравниваем с `rightSideVolume` (default `1`): `<=` -> "хвост" (тонкая диагональ вроде `y`, `,`, `/`) -> зазор `tailRightSideGap` (default `0`); иначе -> "плоский" правый край (`o`, `l`, `m`) -> зазор `flatRightSideGap` (default `1`).
- `DWIDTH = bbx.w + правый_зазор`.

Все четыре порога настраиваются флагами `strike`/`fallback`: `--right-side-count`, `--right-side-volume`, `--flat-right-side-gap`, `--tail-right-side-gap` (в манифесте - соответствующими полями объекта `kerning`, camelCase). Пороги по умолчанию подобраны на глаз по Liberation Sans - для сильно другого исходного шрифта их может понадобиться пересмотреть.

Когда авто-кернинг включён, старый пункт из "known limitations" про формулу DWIDTH из hinted device advance FreeType не применяется: DWIDTH целиком считается этим правилом, а не FreeType-значением. `SWIDTH` (scalable width) при этом по-прежнему считается отдельно из `rendered.advance_x` независимо от режима - он не участвует в `build` (только для BDF-спека/round-trip), так что рассинхронизация с DWIDTH тут ожидаема и не проблема.

## Вертикальные метрики: FONT_ASCENT/FONT_DESCENT (`rasterize.ts`, `verticalMetrics.ts`)

### Откуда берётся значение

`FONT_ASCENT`/`FONT_DESCENT` (позже - `hhea`/`sTypo` ascender/descender в TTF, то, из чего браузер считает высоту line-box при `line-height: 1`) считаются не из метрик исходного векторного шрифта, а из **фактических чернил уже растеризованного, хинтованного битмапа**. Исходная формула (`hhea.ascender / unitsPerEm * pixelSize`, округлённая) для Liberation Sans на 12px давала 11/1 - но реальные чернила базовой латиницы (заглавные, строчные, цифры) занимают только 9 строк сверху и 2 снизу: целый пиксель нижних выносных элементов (`g`, `y`, `p`, `q`, `j`, хвост `Q`) при этом торчал ниже заявленной границы line-box - зазор между строками при `line-height: 1` съедался, и нижние выносные соседних строк могли зрительно соприкасаться.

Функция `computeVerticalMetrics` в `rasterize.ts` вместо этого меряет реальный битмап: берёт базовую латиницу (`A-Za-z0-9`) из уже растеризованных на этом шаге глифов (либо, если её нет вообще - например, страйк только кириллицы - все растеризованные глифы как fallback), находит максимальный реальный ascent и descent среди них, отдаёт оставшийся зазор (`pixelSize` минус реальный descent) под ascent. Для Liberation Sans на 12px это даёт 10/2 - ровно то же, что было в старом hand-made шрифте, потому что там эти числа тоже были подобраны по реальным чернильным границам, а не по метрикам исходного шрифта.

Специально не берётся весь репертуар глифов без ограничения: редкие акцентированные заглавные (`Uring` и т.п.) или математические символы могут по-настоящему выходить за пределы 12 строк (у Liberation Sans, например, кириллическая `Й` реально достигает всех 12 строк) - это нормально и было в старом шрифте тоже; включать их в расчёт раздуло бы "нормальные" метрики ради редких выбросов.

### Почему один страйк не может решить это в одиночку: `verticalMetrics.ts`

Разные начертания одного размера (Regular/Bold/Italic/BoldItalic) должны декларировать **одинаковые** ascent/descent - не потому что так удобнее, а потому что иначе ломается пиксель-в-пиксель совместимость при смешивании начертаний. Сумма (ascent+descent = pixelSize) не меняется в любом случае - `line-height` как таковой не съезжает. Ломается другое: всё, что позиционирует контент относительно того, где именно внутри line-box сидят чернила, а не относительно box'а целиком - например, `Window`/`Titlebar` заголовок сидит во flex-строке фиксированной высоты 34px с `align-items: center`, и смещение ascent на 1px (даже без изменения суммы) сдвигает видимый текст на 1px внутри этой центрированной строки. Так эта проблема и была найдена: у Bold-12, посчитанного независимо от Regular-12, реальный descent оказался на 1px больше (жирные нижние выносные элементы физически толще и чуть глубже), из-за чего его ascent/descent (9/3) разошёлся с Regular-12 (10/2) - сумма та же, но заголовок Titlebar (всегда рендерится `Bold12`) визуально приподнялся на 1px относительно того, что было раньше.

Решение - `verticalMetrics.ts`: первое начертание, застриканное для пары (`fontName`, `pixelSize`) - по порядку в `fonts.json` это всегда `Regular` - меряет свои реальные чернила и кэширует результат в `src-font/{fontName}-{pixelSize}.measurements.json` (например `Standard-12.measurements.json`). Любое следующее начертание того же `fontName`+`pixelSize` (Bold, позже Italic/BoldItalic) читает этот кэш и использует его значения **вместо** собственного измерения - т.е. Bold-12 сейчас декларирует 10/2, как и Regular-12, а не свои реально измеренные 9/3.

Если у более позднего начертания реальные чернила глубже/выше, чем в кэше (ровно как у Bold: реальный descent 3 против закэшированных 2), это не глушится молча - `resolveVerticalMetrics` возвращает список `overflow`, и `cli.ts` печатает `console.warn` с точными числами. Сам глиф при этом не обрезается (браузер рисует контур как есть, метрики влияют только на line-box), риск - чисто визуальный (нижний пиксель жирного `g`/`y`/`p` может зайти в пространство следующей строки при плотной вёрстке) и уже было тем же самым осознанным компромиссом в старом hand-made шрифте (тот тоже использовал одни и те же 10/2 для Regular и Bold).

Кэш-файл `*.measurements.json` - обычный отслеживаемый файл в `src-font/`, не игнорируется (в отличие от `*.report.json`). Чтобы пересчитать метрики с нуля для конкретного размера, достаточно удалить соответствующий `{fontName}-{pixelSize}.measurements.json` и перестрикать заново, начиная с `Regular` (порядок важен - см. "Известные ограничения" ниже).

Кэширование применяется только к **первичному** страйку (`strike`/`strike-all`), не к `fallback`/`fallback-all`: у fallback-BDF своих `FONT_ASCENT`/`FONT_DESCENT` всё равно не доживают до финального шрифта (`merge` сохраняет свойства primary без изменений), так что измерять/кэшировать их не нужно - и опасно, если fallback (например, NotoSansJP с совершенно другими пропорциями иероглифов) вдруг застрикан раньше primary и успел бы засеять кэш неподходящими числами.

## `fonts.json`: манифест-driven пайплайн (`fontsManifest.ts`, `register.ts`)

До этого раздела всё описанное - однократный пайплайн: каждая команда работает с одним шрифтом за раз, а результат (запись `SUPPORTED_FACES` в `typography.ts`, `@font-face`-блок в `index.css`) прописывался командой `register` текстовым сплайсом по anchor-комментариям. Это работало, но с двумя проблемами: во-первых, при трёх и более зарегистрированных гранях легко забыть где какой файл лежит и как его пересобрать с нуля; во-вторых, текстовый сплайс - не то, чему стоит доверять полностью автоматически (сам `register --write` был помечен как "review with git diff", а не "просто доверяй").

`src-font/fonts.json` решает обе проблемы: это единственный источник истины и про то, из чего собирается каждая грань шрифта (`fontName`/`style`/`size`, исходный TTF, промежуточные BDF, кернинг), и про то, что в итоге видит браузер (`SUPPORTED_FACES`, `@font-face`). Схема одной записи (`FaceEntry` в `fontsManifest.ts`), все пути - относительно `src-font/`:

- `fontName`, `style`, `size`, `ttf` - обязательные. `ttf` - имя файла TTF в `src-font/`, оно же имя файла, под которым `push-fonts` копирует его в `public/win-55-ui/font/`.
- `source` + `strikeBdf` - исходный векторный шрифт и куда `strike-all` кладёт результат растеризации. `strikeBdf` - тот самый человеко-редактируемый BDF из шага 4 одиночного пайплайна.
- `fallbackSource` + `fallbackBdf` - **массивы**, той же длины, в том же порядке. `merge-all` сворачивает их в один BDF последовательно, от первого к последнему (второй fallback добирает то, что не нашлось ни в primary, ни в первом fallback, и т.д.) - тем самым можно подключить сразу несколько fallback-источников (например разные шрифты для разных диапазонов Unicode), а не один.
- `mergePath` - куда `merge-all` пишет результат слияния. Существует отдельно от `strikeBdf`, потому что это разные файлы: `strikeBdf` - страйк только основного источника (то, что реально редактируют руками), `mergePath` - страйк с уже подмешанными fallback-глифами (то, из чего собирают TTF). Для грани без fallback-ов `mergePath` не нужен вовсе.
- `ttf`-путь, который реально идёт в `build-all`, - это `mergePath ?? strikeBdf`: если fallback-ов нет, строим прямо из `strikeBdf`.
- `kerning` - см. «Авто-кернинг» выше. Присутствие ключа само по себе включает авто-кернинг для этой грани; поля внутри (`rightSideCount`, `rightSideVolume`, `flatRightSideGap`, `tailRightSideGap`) все опциональны и по отдельности переопределяют дефолты. Пустой объект `{}` означает "авто-кернинг включён, все пороги по умолчанию".

Команды `strike-all`/`fallback-all`/`merge-all`/`build-all` проходят по всем записям манифеста и выполняют для каждой соответствующий одиночный шаг, но только если целевой файл ещё не существует - если существует, запись пропускается с `console.warn`, а не валит весь батч (в отличие от одиночных `strike`/`fallback`, которые без `--force` жёстко падают на существующем файле). Это осознанно: пересборка "только недостающих кусочков" частично собранного набора (например, добавили новую грань в манифест, а остальные уже готовы) - рутинная операция, а не исключительная ситуация, которую нужно подтверждать флагом.

`push-fonts` и `update-register`, наоборот, **всегда** перезаписывают: `push-fonts` копирует `ttf` из `src-font/` в `public/win-55-ui/font/` (это финальный шаг публикации - его смысл именно в том, чтобы обновить уже опубликованное), а `update-register` полностью перегенерирует `src/helpers/generatedFonts.ts` (`SUPPORTED_FACES`) и `src/generated-fonts.css` (`@font-face`-блоки) из манифеста - оба файла помечены баннером "AUTO-GENERATED, не редактировать руками", так что перезаписывать их целиком безопасно и корректно на каждый запуск. `typography.ts` импортирует `SUPPORTED_FACES` из первого, `index.css` подключает второй через `@import` - обе точки подключения прописываются один раз руками при заведении файла, `update-register` их не трогает, только содержимое самих generated-файлов.

## Устройство `build`: от растра к вектору

### Трассировка контуров (`contours.ts`)

Замена AutoTrace - свой однопроходный directed-edge boundary tracer по 4-связности. Для каждого блока закрашенных пикселей одновременно строятся и внешние, и "дырочные" контуры (для `o`, `e`, `8` и т.п.) - без отдельного прохода поиска дыр и без явного сопоставления "какая дыра какому внешнему контуру принадлежит": правило трассировки само гарантирует противоположный знак winding для дыры относительно внешнего контура, а формату TrueType/OpenType для заливки нужен именно плоский список контуров + winding (nonzero fill rule), никакой явной иерархии. Коллинеарные точки схлопываются перед эмиссией - кривых нет вообще, только прямые линии (`lineTo`), потому что трассировать нечего кроме прямых углов растра.

Корректность проверяется инвариантом: сумма signed area всех контуров глифа обязана совпадать с числом закрашенных пикселей (`build.ts` проверяет это на каждом глифе и пишет soft finding при расхождении).

### Координаты и сетка (`unitsPerEm`)

`unitsPerEm = pixelSize * SCALE` (`SCALE = 100` по умолчанию, флаг `--units-per-em-scale`). Каждая координата контура - целое кратное `SCALE` по построению (`coordinate = pixelIndex * SCALE`), поэтому ручная перепроверка em-size, из-за которой раньше "плыл" второй и последующие символы в строке, здесь структурно невозможна - округлять нечего.

`SCALE = 100`, а не что-то около "пиксель = пара юнитов" (как было в старых hand-made шрифтах, где `unitsPerEm` совпадал с итоговым размером в CSS-пикселях, т.е. ~24 для 12px-страйка) - осознанный выбор: `svg2ttf` (см. ниже) применяет собственные проходы упрощения геометрии с фиксированными допусками (~0.3-1.1 юнита). При крупном `unitsPerEm` эти допуски на порядки меньше расстояния между соседними пиксельными границами (100 юнитов) и гарантированно не трогают реальную геометрию; при мелком `unitsPerEm` тот же допуск мог бы случайно схлопнуть тонкие штрихи.

### Отчёт: soft findings vs hard errors

Проверки идут всегда, но не блокируют результат молча. Жёсткая ошибка на уровне глифа (например, вырожденный контур из повреждённого битмапа) - не валит всю сборку: такой глиф просто пропускается (`report.skipped`), пишется причина, а TTF всё равно собирается из всех остальных глифов. Так всегда есть что открыть и с чем свериться по отчёту, а не пустота при первой же проблеме в одном хэндэдитнутом глифе. Всё остальное - soft finding в `report.flagged` (несовпадение размеров битмапа и BBX, нулевой advance width у глифа с чернилами, дубли encoding и т.д.): TTF собирается, находки просто перечисляются в `<out>.report.json` и кратко в консоли. Отдельно есть `selfCheckRoundTrip` - билд перепарсивается и сверяется сам с собой (bbox/advance на пиксельной сетке), чтобы ловить собственные баги сериализации, а не только проблемы входных данных.

Модель специально спроектирована под то, как реально идёт работа: автоматика указывает, куда смотреть, а не заменяет собой визуальную проверку глазами.

## Почему `opentype.js` заменили на `svg2ttf`

Первая версия `build.ts` строила финальный TTF через `opentype.js` (`Font`/`Glyph`/`Path`). Долго всё работало нормально в Chrome, а в Firefox шрифт выглядел "замыленным" и с полупиксельным горизонтальным дрейфом - сначала это списали на особенности рендер-стека Firefox для `@font-face`-шрифтов (см. раздел ниже, это отдельная, реальная и непочинимая история). Но затем всплыл гораздо более серьёзный факт: **`opentype.js` в принципе не умеет писать классический TrueType (`glyf`/`loca`) - только CFF-flavored OpenType.** Это выяснилось трассировкой прямо в `dist`-бандле библиотеки: `Font.prototype.toTables()` вызывает единственную нефорковую функцию `sfnt.fontToTable()`, которая безусловно строит `cffTable`; таблицы `glyf`/`loca` в этой библиотеке есть только в парсере (для чтения существующих шрифтов), но не в райтере.

Это принципиально: механизм, за счёт которого Windows/DirectWrite рисует уже выровненные по пиксельной сетке контуры вообще без размытия (см. `gasp` ниже) - специфичен именно для TrueType. Для CFF-контуров на Windows такого пути нет - там почти всегда работает обычное grayscale-сглаживание, независимо от того, насколько точно выровнена геометрия. То есть первая версия пайплайна физически не могла дать "идеальный" рендер на Windows/Chrome - не из-за багов в собственной геометрии, а из-за формата контейнера.

Заменили на **`svg2ttf`** (тот же `nodeca`/fontello-экосистема, что и уже использующийся `lv_font_conv`) - он пишет настоящие `glyf`/`loca`-таблицы из SVG-путей. Наши контуры - только прямые линии, поэтому сериализация тривиальна (`svgFont.ts`: `contourToSvgPath()` эмитит `M x,y L x,y ... Z` вместо вызовов `path.moveTo`/`lineTo`). `opentype.js` из пайплайна не исчез - он по-прежнему парсит исходные векторные шрифты в `rasterize.ts` и используется для `selfCheckRoundTrip` (чтение TrueType он умеет прекрасно, проблема была только в записи).

Бонус: `svg2ttf` уже по умолчанию выставляет `head.flags = 0x000B` (биты "baseline at y=0", "LSB at x=0", "force integer ppem for scaler math") и `OS/2.fsSelection = REGULAR | USE_TYPO_METRICS` - то есть ровно то же самое, что нашлось в старом hand-made шрифте при побайтовом сравнении таблиц, без единой лишней строчки кода с нашей стороны.

## `gasp`: почему шрифт вообще выглядит чётко на Windows

`svg2ttf` не пишет таблицу `gasp` вовсе. У старого hand-made шрифта она есть: один диапазон на весь ppem (`0..65535`) с флагом `DOGRAY` (grayscale, без `GRIDFIT`). Это именно то, что позволяет Windows рисовать уже выровненный по сетке контур без сглаживающего "дребезга" - раз AA включено, но каждой границе просто нечего усреднять, потому что она и так падает точно на границу пикселя.

`build.ts` дописывает такую же таблицу постфактум через `sfnt.ts` (`insertSfntTable`) - маленький, независимый от gasp как такового бинарный инструмент: перечитывает directory таблиц sfnt-контейнера, добавляет новую запись, пересчитывает офсеты/паддинг/чексуммы (включая `checkSumAdjustment` в `head`, который обязан учитывать вставленную таблицу).

## `cmap`: почему большие (fallback-merged) шрифты не грузились в браузере

После перехода на `svg2ttf` небольшие шрифты собирались нормально, а вот `Standard-Regular-12` (16933 глифа после fallback-мёрджа с NotoSansJP) браузер отказывался грузить с ошибкой OTS (`OpenType Sanitizer`, санитайзер, который и Chrome, и Firefox прогоняют по любому скачанному `@font-face`-шрифту): `cmap: Failed to parse format 4 cmap subtable`.

Причина - в самом `svg2ttf`: его writer для cmap format 4 всегда использует полный `glyphIndexArray` + 16-битный `idRangeOffset` (никогда не применяет более компактный `idDelta`-шорткат). При достаточном числе сегментов/глифов в BMP-диапазоне (что рутинно случается после fallback-мёрджа) это поле переполняется. OTS ловит битую format-4-подтаблицу и, по спецификации, ронит **всю** таблицу `cmap` целиком - а с ней и весь шрифт.

Чинить кодирование format 4 внутри `svg2ttf` смысла не было: он и так безусловно пишет ещё и format 12 (полный диапазон Unicode, 32-битные поля - переполниться нечем), а format 12 - строгое надмножество format 4. Более того, парсер `opentype.js` сам предпочитает подтаблицу `(3,10)`/format 12 таблице `(3,1)`/format 4, если обе присутствуют (порядок перебора подтаблиц такой, что последняя валидная запись в directory побеждает). Значит, format 4 никому и не был нужен. Решение - `cmap.ts` (`stripCmapFormat4`): вырезать из уже собранной таблицы `cmap` подтаблицы format 4 и связанные с ними заголовки, пересобрать directory (с сохранением шаринга одного и того же блока данных между несколькими заголовками, если он есть), заменить таблицу через `sfnt.ts` (`replaceSfntTable`).

## Известные явления, которые НЕ чинятся на уровне пайплайна

Пара визуальных артефактов расследовались долго, но были в итоге признаны характеристиками самого рендер-стека браузера, а не багами шрифта/пайплайна:

- **Firefox: горизонтальный суб-пиксельный дрейф.** Ни старый hand-made шрифт, ни новый не имеют встроенных TrueType hint-инструкций (`fpgm`/`prep`/побайтовые hint-программы на глиф) - у обоих "хинтинг" исчерпывается точными координатами контура. Firefox исторически прогоняет загруженные (`@font-face`) шрифты через свой собственный FreeType-based текстовый стек отдельно от системных шрифтов, и без реальных hint-инструкций там нет привязки к пиксельной сетке - только сглаживание по плавающим координатам. Отсюда - лёгкое накопление суб-пиксельной погрешности на протяжении строки. В Chrome (DirectWrite на Windows) тот же безынструкционный шрифт рендерится идеально ровно. Настоящий фикс потребовал бы генерации реальных TrueType hint-инструкций (например, через `ttfautohint`) - то есть возврата внешней зависимости, от которой пайплайн специально уходил.
- **ClearType/LCD-сглаживание: лёгкий цветной ореол по краю штрихов.** Инвариантная особенность LCD-subpixel-сглаживания как такового - его фильтр-ядро по конструкции "размазывает" покрытие на соседний субпиксель даже у идеально выровненной по сетке границы. Не зависит от точности геометрии шрифта. `-webkit-font-smoothing: none` (см. следующий пункт) переключает Chromium на grayscale-AA вместо ClearType, но не отключает антиалиасинг полностью - стандартного кросс-браузерного способа заставить браузер рисовать текст строго bilevel не существует. Настоящее решение потребовало бы рендерить текст через `<canvas>` побитмапно вместо настоящего `@font-face`-текста - совсем другая архитектура, вне рамок этого пайплайна.

Мимоходом при этом расследовании нашли и починили реальный, не платформенный баг: `index.css` содержал `-webkit-font-smoothing: never` - невалидное значение свойства (валидные: `auto | none | antialiased | subpixel-antialiased`). CSS молча отбрасывает объявление с невалидным значением, так что эта строка не делала вообще ничего, всегда откатываясь к `auto`. Исправлено на `none`.

## Другие найденные и исправленные баги

- **`FONT_ASCENT`/`FONT_DESCENT` не суммировались в `PIXEL_SIZE`.** `rasterize.ts` вычислял их независимым округлением из ascent/descent исходного векторного шрифта - гарантии, что сумма совпадёт с номинальным размером страйка, не было. `build.ts` использует эту сумму как `hhea.ascender/descender` - а это именно то, из чего браузер считает высоту line-box при `line-height: 1`. Недостача в 1 юнит давала systematic сдвиг текста на 1px вниз (лишний leading делится пополам сверху/снизу). Исправлено: `descent` теперь всегда выводится как `pixelSize - ascent`, а не округляется отдельно - сумма точна по построению.
- **`USE_TYPO_METRICS` не был выставлен.** Даже после фикса выше сдвиг никуда не делся - оказалось, что браузеры по умолчанию (без этого бита в `OS/2.fsSelection`) считают line-box не по `sTypoAscender/sTypoDescender` (которые как раз равны нашим точным ascent/descent), а по `usWinAscent/usWinDescent` - а их `opentype.js` вычислял автоматически из фактических экстремумов чернил по всем глифам собранного шрифта, что с нашими значениями никак не было связано. С переходом на `svg2ttf` бит уже выставлен библиотекой по умолчанию - отдельный код не нужен.

## Структура `scripts/font/src/`

TypeScript со своим `tsconfig.json` и build-шагом (`npm run font:build`, инкрементальный) - единственный инструмент в `scripts/` на TS, а не на обычном JS, как остальные `*-cli.js`: домен достаточно сложный (геометрия контуров, бинарные форматы BDF/sfnt), чтобы типы окупались.

| Файл | Назначение |
|---|---|
| `cli.ts` | Разбор argv, диспетчеризация подкоманд, `usage()`/`fail()` |
| `cli-args.ts` | Ручной сканер `--flag value` (без внешних зависимостей типа yargs) |
| `paths.ts` | `projectRoot`/`srcFontDir`/`publicFontDir`/`fixturesDir`/`fontsManifestPath` |
| `registry.ts` | `SIZES` - зеркало того же списка в `typography.ts`, для предупреждения при нестандартном размере страйка |
| `types.ts` | `BdfFont`, `BdfGlyph`, `Bbx`, `Point`, `Contour` и т.д. |
| `bdf.ts` | `parseBdf()`/`writeBdf()` - парсер и сериализатор BDF |
| `fontsManifest.ts` | `FaceEntry`/`FontsManifest`, `parseFontsManifest()`/`loadFontsManifest()` - схема и валидация `fonts.json` (см. выше) |
| `rasterize.ts` | Векторный TTF/OTF -> `BdfFont` через `lv_font_conv`'s bundled FreeType WASM (`fontface_create`/`glyph_render`/`glyph_exists`, вызывается напрямую в обход высокоуровневого CLI пакета); также авто-кернинг (`autoRightGap`) и измерение вертикальных метрик по реальным чернилам (`computeVerticalMetrics`, см. выше) |
| `verticalMetrics.ts` | `resolveVerticalMetrics()` - кэш `FONT_ASCENT`/`FONT_DESCENT` на диске (`{fontName}-{pixelSize}.measurements.json`), общий для всех начертаний одного размера (см. выше) |
| `contours.ts` | Битмап глифа -> контуры (собственный boundary tracer, см. выше) |
| `svgFont.ts` | Контуры -> SVG path -> SVG-font XML-документ -> вызов `svg2ttf` |
| `sfnt.ts` | Низкоуровневые операции над sfnt-контейнером: `insertSfntTable`/`getSfntTable`/`replaceSfntTable`, генерация `gasp` |
| `cmap.ts` | `stripCmapFormat4` - вырезание переполняющейся format-4 cmap-подтаблицы |
| `build.ts` | Оркестрация: BDF -> глифы -> `svgFont.ts` -> патчи `gasp`/`cmap` через `sfnt.ts` -> отчёт `flagged`/`skipped` |
| `merge.ts` | Донабор недостающих глифов из fallback BDF, `summarizeBackfill()` (компактный range-summary, capped на 8 диапазонов) |
| `register.ts` | `buildSupportedFacesModule()`/`buildFontFaceCss()` - генерация полного содержимого `generatedFonts.ts`/`generated-fonts.css` из `FontsManifest` (см. выше) |
| `svg2ttf.d.ts` | Рукописная декларация типов - у пакета `svg2ttf` официальных `@types` нет |

Каждый `*.ts` (кроме `svg2ttf.d.ts`) имеет пару `*.test.ts` на `node:test` (первый прецедент тестов в репозитории вообще, `npm run font:test`). Тесты по возможности не зависят от живых файлов в `src-font/` (которые пользователь может в любой момент перегенерировать/удалить) - либо замороженная фикстура (`src/__fixtures__/`), либо растеризация на лету из стабильного исходника (`src-font/liberation_sans/`).

## Известные ограничения / что не доделано

- Allowlist "пустой глиф - это нормально, не считать дырой" в `merge.ts` сейчас - только `space`/`nbspace`; скорее всего придётся расширять по мере использования новых fallback-источников.
- Правило авто-кернинга (см. выше) - эвристика (дефолтные пороги `rightSideCount`/`rightSideVolume` = 1), подобранная на глаз по Liberation Sans; для сильно другого исходного шрифта пороги может понадобиться пересмотреть через `kerning` в `fonts.json`.
- `merge-all` не умеет частичного слияния: если для грани не хватает хотя бы одного файла из цепочки (`strikeBdf` или любой `fallbackBdf`), пропускается вся грань целиком, а не сколько получится.
- `strike-all`/`fallback-all`/`build-all` не перезаписывают существующий файл никогда (нет batch-эквивалента `--force`) - для принудительной пересборки одной конкретной грани сейчас нужно удалить файл руками или вызвать одиночную команду (`strike`/`build`) с `--force`/явным `--out` напрямую.
- Real TrueType hinting instructions (`fpgm`/`prep`/per-glyph bytecode) в пайплайне принципиально нет - см. раздел про Firefox выше. Если это когда-нибудь станет проблемой достаточно серьёзной, чтобы оправдать `ttfautohint` как зависимость (нарушив "zero externally-installed tools"), это отдельное архитектурное решение, не мелкий фикс.
